# Core changes

Every change to the shared core (listed in [OWNERS.md](OWNERS.md)) gets an entry here: what changed, why, and how existing models keep working. Newest first.

## 0.1.2

### Version from one source

1. **`models.json`, `src/mashbox/__init__.py`, `pyproject.toml`:** the release version is written once, as the `version` field of `models.json`. `mashbox.__version__` reads the packaged copy, and `pyproject.toml` takes it from `mashbox.__version__` (`dynamic = ["version"]`). The sync check fails when `pyproject.toml` writes a version of its own or `__init__.py` disagrees with `models.json`. **How callers keep working:** `mashbox --version`, `mashbox env` and `mashbox.__version__` give the same string as before.

### `mashbox --help` lists `tpu`

1. **`cli.py`:** the top-level parser lists `tpu` with a one-line help; the `tpu` commands are still parsed by `mashbox.tpu`. **`tpu/__init__.py`:** `down`, `status`, `ssh` and `tunnel` have help lines. **How callers keep working:** every command line parses as before.

### Speculative decoding (off by default)

1. **`runtime/engine.py`, `runtime/sampler.py`, `models/qwen3_8_27b/model.py`, `models/qwen3_8_27b/spec.py`, `cli.py`, `hub.py`:** an optional speculative decoding path with the model's own multi-token-prediction head: `--mtp K` drafts K tokens per verify pass (1 to 3) from the draft file `models.json` lists for the model (kind `draft`); `--mtp-file` gives a local one, sha256 checked. One chip only; requests with penalties decode without it. **How callers keep working:** without `--mtp` (or with `--mtp 0`) the engine decodes as before and the draft file is never fetched. In this release `--mtp` and `--mtp-file` are not listed in `--help` and no model's draft file is in `models.json`, so `mashbox run` decodes without speculation.

### Chat speed: no decode compiles mid-reply, server timings, Stop on a half-closed socket

1. **Warm-up** (`Engine.warm_decode`, called by `mashbox run`): runs every decode program a reply can reach (each attention window 128 ... ctx, greedy per row bucket, sampled at S rows) before ready, then clears the slot states. Measured on a TPU v6e-1 (ctx 32768 x 1 slot): a 10-turn chat had 6 decode compiles of ~5 s each inside replies before, 0 after; turn 1 showed 20.0 tok/s before, 38.0 after. Cost: 18 programs, 65.0 s on an empty compile cache, 5.6 s from it. Outputs unchanged (greedy and seeded, before vs after).
2. **`timings`** (llama-server's block: prompt_n, prompt_ms, predicted_n, predicted_ms, predicted_per_second, cache_n, queue_ms) on the last chunk, the usage chunk and plain responses, and in the request log. MASHBOX Chat shows the server's predicted_per_second when it is there.
3. **Stop:** a streamed request also ends when its socket reads EOF (select + 1-byte MSG_PEEK, as llama-server), not only when a write fails; behind an SSH tunnel a write may never fail. CPU test `test_client_half_close_ends_generation`.
4. **Every program before ready, committed slot state** (`Engine.warm`, replaces `warm_decode`): the warm-up also runs every prefill program `prefill()` can choose (`Engine.prefill_shapes`: each chunk bucket x attention window x row bucket), compiling them in 8 threads first, then running each once. The slot state is made on the chip as committed arrays when the weights sit on one device (as `shard.py` does on a mesh): JAX keys a program on whether each argument is committed, and a fresh state was not, so the first prefill and decode after each new state were programs of their own that no warm-up ran (the 5.4 s sampled compile left open above). Measured on a TPU v6e-1 with an empty compile cache: ctx 2048 x 8 runs 102 prefill + 20 decode programs, ready in 339.9 s the first time and 47.2 s from the cache; ctx 32768 x 1 runs 50 + 18, ready in 122.1 s. After ready, the only compiles in a 3-turn chat at 2048 x 8 and a 10-turn chat plus 5 more requests at 32768 x 1 were `put` and `stack` (0.14-0.2 s). First reply at 2048 x 8, Recommended preset: 32.7 tok/s, first token 0.36 s (was 17.4 tok/s and 7.42 s on main). Outputs unchanged (greedy chat 3/3 turns, seeded and greedy requests). CPU test `tests/cpu/test_engine_warm.py` (no program added after the warm-up across prompt lengths, rows, greedy and sampled, cached and restored turns).
5. **Sampled rows and the shipped compile cache:** sampled rows run all S rows (32.7-33.0 tok/s for one user at 8 slots, 38.1 at 1 slot). The compile cache shipped for TPU v6e with JAX 0.11.2 holds every program the warm-up compiles: with the weights on disk, a start on TPU v6e-1 is ready in 69.6 s at 2048 x 8 and 32.6 s at 32768 x 1, against 326.6 s on an empty compile cache.

### Hy-Nomas: one world page, card licence lines, its compile cache

1. **`tools/hf_github_sync_check.py`, `templates/hf/card-world.md`:** the world card says where the upstream LICENSE file comes from (`upstream_licence_file(m, source=True)`) and states the licence of our own files in the model's Hugging Face repo, read from each file's row in the model's `upstream.json` (`license`, chosen by people, never derived). The licence check fails an own file without one. A model whose only `files[]` row is a compile cache still says where its weights come from. **How existing models keep working:** the other card templates are unchanged and the Qwen3.8-27B card renders byte-identical; no other model has an own file in its Hugging Face repo.
2. **`tests/cpu/test_module_shell.py`, `tools/numbers_allowed.txt`, `tools/docs_lint_allow.txt`:** the Hy-Nomas world page has one source, `src/mashbox/models/hy_nomas/page.html` (the installed package serves it). The copy in `apps/hy-nomas/` is gone; the page list and the allow lines name the package path, and `test_world_page_has_one_source` fails on a second copy.
3. **`templates/hf/card-world.md`:** the world card no longer says "One install and one command, from a new Google account to a running model" (it takes more steps than that). Its quickstart is followed by the model's `notes` field, which for Hy-Nomas gives the SSH tunnel line and the address to open. **How existing models keep working:** only world cards use this template; the Qwen3.8-27B card renders byte-identical.

### Prompt cache in host memory

1. **`runtime/engine.py`, `cli.py`:** a conversation that loses its slot to another request is copied to host memory and restored on an exact token match when it comes back, as llama-server's host-memory prompt cache. Prompts also resume at saved points at user messages. Options, with llama-server's names: `--cache-ram MIB` (default 8192, `0` turns it off), `--ctx-checkpoints N` (default 8), `--checkpoint-min-step N` (default 8192). Saved points carry the API key scope of the request that made them, as the slot cache does. **How callers keep working:** on by default; answers are unchanged (with temperature 0 and a fixed seed a restored conversation gives the same tokens); `--cache-ram 0` gives the slot-only cache of 0.1.1.

### `mashbox tpu up --chip` and chips by type

1. **`models.json`:** the `chips` rows are by the type people rent: TPU v5e, TPU v6e, TPU v5p slice (v5p-8) and TPU v6e slice (v6e-4). A row names the host (`accelerator`), the Google type (`gcloud_type`), runtime, chip count and tensor parallel size. The generated views (README, chips table, FAQ chips block, model pages, `llms.txt`) list all four.
2. **`src/mashbox/tpu/__init__.py`:** `mashbox tpu up <model> --chip <host>` creates any host the model is supported on, from those rows (for Qwen3.8-27B: `v6e-1`, `v5e-4`, `v6e-4`). **How callers keep working:** without `--chip`, `up` creates the model's default chip as before.
3. **`cli.py`:** `--tensor-parallel-size` defaults to the chips of the host, at most 4 (1 on a TPU v6e-1, 4 on a v5e-4 or v6e-4). An explicit value works as before.

### Server: requests of a gone client end, and the queue has a cap

1. **`runtime/server.py`:** a request whose client hangs up is ended while it waits or runs, streamed or not; a waiting request of a gone client never runs; at most `MAX_WAITING` (256) requests wait, more get 429 with `Retry-After`. **How callers keep working:** clients that stay connected see no change.

### The chat relay is guarded

1. **`ui/chat/__main__.py`** (`python -m mashbox.ui.chat --api ...`, port 8801): every request goes through `runtime.guard` (Host names this machine or `--host`; a browser's Origin is the relay's own; POST is `application/json`). The relay sets the upstream Host itself, so the model server's guard never sees the browser's; without this a page whose domain is re-pointed at 127.0.0.1 could read model replies through port 8801. No token: it is a documented plain route. **How callers keep working:** the page, curl with its JSON header and scripts on 127.0.0.1 or localhost pass unchanged. **Test:** `tests/cpu/test_chat_relay_guard.py` (refused page requests, normal use).

### The desktop app server is guarded

1. **`ui/app/__init__.py`:** every request goes through `runtime.guard` (Host names this machine; a browser's Origin is the app's own; POST is `application/json`). `/api`, `/v1` and `/health` also need this launch's token in `X-Mashbox-Token`; the app's own pages carry it in `<meta name="mbx-token">` and the window, the screens and the chat page send it. The token is never printed (stdout goes to the desktop app's runtime.log) and never set as a cookie (a cookie on 127.0.0.1 goes to every port). `/v1` and `/health` answers are passed on as JSON, event stream or text only (anything else becomes `application/octet-stream`, with `nosniff` and `CSP: sandbox`) and never set cookies. The app's pages refuse framing by other sites.
2. **World page on its own origin:** the world model server's page, files, API and stream are served from a second port (`--world-port`, default `--port` + 1, any free port when that one is taken) that has no `/api`, `/v1` or token; `/m/world/` on the app port redirects there. The stream relay forwards only WebSocket headers plus the browser's real Origin (never Cookie), and needs an allowed Origin. A world server with an Origin check must allow `http://127.0.0.1:<world port>` and `http://localhost:<world port>`.
3. **Inputs:** TPU chip names must match the Cloud TPU name pattern, a model must be a catalog row with `cloud`, a zone one of its zones, and `max_hours` above 0; values go to `mashbox tpu` as `--opt=value`.
4. **Pages:** links in the window load only when http(s) (no `mailto:javascript:`), never at `/v1`, `/api` or `/health`; chat Markdown takes `mailto:` only with an address; the catalog's `chat.source` link must be http(s); the Codex config takes the server's model id and address only when they are plain printable text, as TOML strings.
5. **How callers keep working:** the desktop wrapper loads `http://127.0.0.1:<port>/` as before and needs no change. `make_handler()` now takes `(token, ports, host)`; `start(host, port, world_port)` binds both listeners. **Tests:** `tests/cpu/test_app_security.py` (+ `tests/cpu/app_js_checks.js`, the real page scripts in Node), `tests/cpu/test_app_module.py` updated.

### Agent API review fixes

1. **`runtime/engine.py`:** `on_step` may return the indexes of prompts to end now; those rows stop at that step with finish `cancel`, as a padding row would (`Engine._cancel`). Their prompt points were saved before decoding, so the prefix cache keeps them. Compatible: an `on_step` that returns nothing (every caller before this) behaves as before.
2. **`runtime/server.py`:** a request whose client hangs up mid-stream, or whose stop string is found, is ended at the engine's next step. Before, the engine decoded it to the end of the turn (up to the end of the context) for nobody, holding the slot. The request line is still logged, with `finish` `client_closed`. `/v1/completions` streams now send their final chunk when a stop string ends them. Responses streams: the `response.output_item.added` event of a function call or custom tool call carries empty `arguments` / `input`, and the value comes in the delta and done events. It carried the whole value, so a client that appends the deltas to the added item, as OpenAI's SDK does, got the arguments twice.
3. **`runtime/agents.py`:** tool results are put in the order of the calls they answer, matched by `tool_call_id` / `tool_use_id` / `call_id`, when a client sends them in another order (the chat template has no ids, so the order is the only link). Results already in call order render exactly as before, so cached prompts stay valid.
4. **Tests:** `tests/cpu/test_agent_api.py` (result order on all three APIs, the Responses added item, a stop string and a client hang-up end the row) and `tests/cpu/prefix_cache_checks.py` P6 (an ended row stops at once, the other row decodes the reference tokens, the next turn is served from the cache).

## 0.1.1 (2026-10-28)

### Inference server and chat template security fixes

1. **`runtime/chat.py`:** control tokens come only from the template. A literal `<|im_end|>`, `<|im_start|>` or `</tool_response>` in a message, tool result, tool call or tool definition is tokenized as plain text, so text an agent reads cannot forge a user or system turn. A chat whose strings hold no control-token text gets the same ids as before (one pass; checked with the shipped Qwen tokenizer).
2. **`runtime/server.py`:** every request passes `runtime/guard.py`: Host must be localhost, 127.0.0.1, [::1], an IP address or the server's own `--host` (a DNS-rebinding page is refused, 403); a present Origin must be the server's own (403); a POST must be `application/json` (415), so a web page cannot send one without a CORS preflight, which the server never approves. Clients that are not browsers (curl, SDKs, coding agents) pass as before. `/health` stays open.
3. **API keys, `cli.py` and `runtime/server.py`:** `--api-key-file FILE` (one key per line) or `MASHBOX_API_KEY=k1,k2` makes every `/v1` request need a key (`Authorization: Bearer` or `x-api-key`, 401 otherwise). On a `--host` that is not loopback a key is made once in `~/.config/mashbox/api-key` (mode 0600) and only its path is printed. On 127.0.0.1 nothing changes for the documented agent setups. A key source that holds no key (an empty key file, `MASHBOX_API_KEY` with only commas) stops the start instead of serving with no key.
4. **`runtime/engine.py`:** every prefix-cache point belongs to the scope (API key) of the request that made it, and a prompt resumes only from its own scope's points, so one key's prompts are never served from, or reported as cached by, another key's. Without keys there is one scope, as before.
5. **Tests:** `tests/cpu/test_serve_security.py` (each refused request against the real handler).
6. **`tpu/__init__.py` (tunnel):** `mashbox tpu up` / `tunnel` bind the local port themselves and keep it for the whole session (tunnel drops included), relaying each connection to the SSH forward, which listens on a Unix socket in a private (0700) directory with its log; so another user of the same machine can neither take the port nor answer in the chip's place. "Server ready" needs our SSH process running; a forward SSH cannot set up stops with its message and the take-down command. Chip names, zones and projects are checked before any gcloud call. Tests: `test_tunnel_port_is_held_and_its_forward_is_private` (fails on the code before); the fake gcloud serves the forward on the Unix socket.

### Request guard for the local servers

1. **`runtime/guard.py` (new, stdlib only):** `Guard(hosts, origins, token, key, cookie).check(method, path, headers, auth)` returns None or (status, message). Host must be localhost, a name under .localhost, an IP address or a configured name (any port, since a tunnel may forward another local port); Origin absent or the server's own (or listed); POST bodies `application/json`; WebSocket upgrades carry an allowed Origin; with `auth=True`, the per-launch token (`X-Mashbox-Token` header, the named cookie, or `?token=` on a WebSocket handshake) and the API key (`Authorization: Bearer` or `x-api-key`). `MASHBOX_ALLOW_HOSTS` / `MASHBOX_ALLOW_ORIGINS` add names and origins. Helpers: `new_token()`, `set_cookie()`, `loopback()`. Why: a web page can drive or, after DNS rebinding, read servers on 127.0.0.1. Compatible: the inference server uses it (entry above), and every documented client (curl with its JSON header, Claude Code, Codex, Pi, SDKs) passes it unchanged.
2. **Tests:** `tests/cpu/test_guard.py` (the request shapes a web page can send are refused, documented clients pass, token and key sources).

### `mashbox tpu up` deletes a create that may have gone through

1. **`src/mashbox/tpu/__init__.py`:** a plain create that ends in an error that is not a clear refusal (an expired sign-in, or an error `up` does not know), or that was made and then never reached READY, is deleted by its exact name in that zone before `up` tries the next zone or stops. When that delete fails too (the sign-in is still expired), `up` stops with the chip's name, zone and both delete commands (`mashbox tpu down <name>` and the `gcloud compute tpus tpu-vm delete` line). A queued request that ends in such an error counts as made: it is watched like the others (it can be the one granted) and deleted by name when `up` ends. A plain node or queued request that already existed under that name ("already exists") was not made by this command: `up` never uses or deletes it. A queued request that is already gone counts as deleted ("not there"); a failed delete prints its `gcloud` line. Why: when the sign-in expired during a create, `up` stopped with "gcloud is not signed in" while Google went on creating the chip, without telling the person, and an unknown error on a queued request was read as a refusal. Compatible: same commands and options; clear refusals (no capacity, quota, no access, API off, billing) behave as before.

3. **`life.sh`:** the time left is read after the script fetch, so a reboot seconds before the deadline cannot arm a calendar time already past (which never fires); 2 s or less left deletes at once.
4. **Tests:** `tests/cpu/fake_gcloud.py` gains `accepted-auth` and `accepted-internal` for plain creates and queued requests (made, then the call fails; `accepted-auth` leaves the sign-in expired). `tests/cpu/test_tpu_cli.py` covers each of these cases.

### Install on a TPU VM (Python 3.12 through uv)

On the TPU VM image `v2-alpha-tpuv6e` (Ubuntu 22.04, Python 3.10.12, pip 22.0.2):

1. **Install line (README, `docs/google-cloud.md` step 7, `AGENTS.md`, `templates/hf/card-llm-tpu.md`, `docs/_templates/model.md`):** `python3 -m pip install "mashbox[tpu]"` failed on the chip with `No matching distribution found for jax[tpu]==0.11.2`, because jax and jaxlib 0.11.2 need Python 3.12. The line is now `python3 -m pip install uv && python3 -m uv tool install --python 3.12 "mashbox[tpu]"`: uv brings its own Python 3.12 and puts the `mashbox` command in `~/.local/bin`, so commands use `~/.local/bin/mashbox` in place of `python3 -m mashbox`. Measured on the chip: 6.9 s, 5.6 s and 4.8 s for the whole install (three new users). Compatible: the package and CLI are unchanged; `python3 -m mashbox` still works from any Python 3.12 environment that has it. Other card templates (`card-world.md` and the rest) and `docs/models/hy-nomas.md` kept the old line in this version; the TPU VM images have Python 3.10, so the same change applies to them.
2. **`pyproject.toml`:** `requires-python` is `>=3.12` (was `>=3.10`). Why: the `tpu`, `cpu` and `dev` extras pin jax 0.11.2, which needs 3.12; with `>=3.10`, pip on 3.10 installs the package and then fails on JAX with a less clear message. Compatible: no supported setup ran on 3.10 or 3.11.
3. **`.github/workflows/ci.yml`:** CPU tests run on Python 3.12 (was 3.10), for the same reason: `pip install -e ".[dev]"` cannot install jax 0.11.2 on 3.10.
4. **`hub.py`:** downloads from Hugging Face use plain HTTPS unless the user sets `HF_HUB_DISABLE_XET` (the module sets it to `1` with `setdefault`, before `huggingface_hub` is imported). Why: Xet downloads of the 26.9 GB weights file on new TPU VMs could stop with `HTTP 429 Too Many Requests` from the Xet CDN (ending `mashbox run` with a traceback) or stall, while HTTPS finished at 200 to 230 MB/s in europe-west4-a. Compatible: same files, same sha256 checks; `HF_HUB_DISABLE_XET=0` gives the old behaviour.
5. **`CONTRIBUTING.md`, `.github/ISSUE_TEMPLATE/bug.yml`:** the env command is `~/.local/bin/mashbox env`.
6. **`runtime/server.py`:** the batching loop waits up to `GATHER_S` (20 ms) after the first queued request for others before it starts a batch (requests with `"merge": false` do not wait). Why: requests sent together reach the queue a few milliseconds apart, so the first one ran alone and the rest waited for its whole answer. Measured on TPU v6e-1 with Qwen3.8-27B (8 users, 128 new tokens each, greedy): 8 users in a closed loop for 60 s went from 76.9 to 258.0 tokens/s in total (median request 7.74 s to 3.97 s); 8 streamed requests sent together went from a first token at 3.51 s for 7 of them to 0.11 s for all 8. Cost: one user alone gets the first token 20 ms later (32 ms to 52 ms) and 37.45 instead of 37.75 tokens/s (one run each). Compatible: same routes, outputs and options; the module docstring now says that requests arriving while a batch runs wait for it to finish.

### Qwen3.8-27B weights file

1. **`hub.weights_file`:** picks from the `files[]` rows whose `kind` is `weights` (a row without `kind` counts as weights), the one marked `"default": true` when no name is given, else the first. ### Coding agents: Anthropic Messages, OpenAI Responses, tool calls, prefix cache
