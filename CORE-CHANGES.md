# Core changes

Every change to the shared core (listed in [OWNERS.md](OWNERS.md)) gets an entry here: what changed, why, and how existing models keep working. Newest first.

## 0.1.3

### A second start loads the programs it compiled (executable table, local only)

1. **`runtime/programs.py` (`Table`, `Dispatch`), `runtime/engine.py` (`Engine.warm`):** the warm-up builds each program of the serving path into a table of executables keyed by its call (program name, static arguments, argument shapes and dtypes), and each call runs its executable without tracing. A call the table does not hold runs through jit and counts as a compile (after ready it is logged as `compile_after_ready`, as before).
2. **`cli.py` (`aot_dir`, `cmd_run`):** after the warm-up the table is saved under the compile cache folder in `aot/<deployment id>/`, written into a new 0700 folder that is renamed into place; `manifest.json` names each file with its sha256, size and the sha256 of its full call key, plus the deployment id and the program list sha. The next start of the same deployment loads it before the warm-up, so the warm-up neither traces nor lowers those programs. Log events: `{"event": "aot_table", "phase": "load" | "check" | "save", ...}`, or `"used": false` with the reason.
3. **Trust and identity (`runtime/programs.py`, `runtime/compile_key.py`):** nothing is unpickled before the folder and its parent are this user's and not group or world writable, every file is a regular file of this user (no links), the folder holds exactly the manifest's files, and every file's size and sha256 match it; an extra, missing, changed or swapped file refuses the whole table. The deployment id also binds the sha256 of the installed mashbox source, the chip topology (device count, cores per chip, tp, mesh shape, the devices used) and, while speculation runs, the drafter's identity (`cli.drafter_identity`: kind, id@version, the sha256 of the weights it loaded and the k rule; the draft length is in the components). A table built for another program list is dropped before ready and every program compiles. With speculative decoding on there is no table: the warm-up compiles its programs through jit, outside the table. The table is made and used by one user on one machine: no download installs one (the compile cache archive importer installs flat files only).
4. **The warm-up skips running what the table proves (`Engine.warm`, `programs.proven`):** a program loaded from the table is not run again before ready when the call's own argument checks (pytree, shapes and dtypes, committed shardings and layouts) pass without running it and the device has room for its temporaries and outputs; only programs that ran are saved, so each loaded one ran in the start that saved it. Only representatives still run: the first (smallest) program of each prefill row bucket and the first of each decoder function (`dec`, `decs`); every other loaded program (other attention windows, step widths, row buckets) first runs in a request. If a representative fails, including a device error that shows only at the warm-up's final barrier, the table is quarantined and dropped and every program compiles and runs as without it. The `warm` log event counts `run_programs` and `skipped`, with `run_why` for each loaded program that ran and `fallback`. `MASHBOX_WARM_RUN_ALL=1` runs every program.
5. **A loaded program that fails in a request (`programs.TableFailed`, `Table.fail`, `Server.table_failed`):** any error a program loaded from the table raises when it is called (at launch, including out of memory or a donated buffer, or in the executable's own argument check) is a table failure: the table folder is renamed to `.refused-<name>-<time>-<pid>` beside it (never loaded again; the next start saves a new table), the table is dropped, and the call never runs through jit in its place. The engine's process then ends instead of warming again where it said ready (every compile there would be a compile after ready, and a failed device call restarts the engine's process). Behind the HTTP front (`mashbox run`), the worker sends one fatal error frame that names the table failure and exits (`Worker.table_failed`); the front answers 503 (Anthropic route 529) while it starts a new worker, starts every later worker without the table (`MASHBOX_AOT=0`, so a folder that could not be closed is never loaded again), times that start as a first start (it compiles every program before it says ready, so the restart limit does not apply to it), and sends a request of that call whose client has received nothing once more; the others get the error. /health's compiles after ready stay 0. A one-process server (`Server.table_failed`) gives every job of the call the error and exits with code 70.
6. **How callers keep working:** same commands and options. `MASHBOX_AOT=0` turns the table off (the compile cache path as before). A refused or unreadable table, an entry that does not load, and a failed save each compile instead; ready still comes after the full warm-up, and zero compiles after ready is checked the same way. A start that refuses its table folder, or drops it for another program list, moves it aside as `.refused-<name>-<time>-<pid>` and saves a new table in its place (`programs.set_aside`). After a start saves a new table, `aot/` keeps the current deployment's table, the newest other one used in the last 14 days (a start of the previous version finds its table) and the newest two refused tables from the last 14 days, and removes the rest (`programs.prune`). Every part folder an interrupted save left is removed before each save and by prune, however young: a save holds a lock on its part folder while it writes it, so only folders no live save holds go. A writer of an older build takes no such lock; its save can fail, or leave a table with files missing that the next start refuses before reading it, so that start compiles every program (one warm skip lost, nothing unchecked loaded). A table another process uses is never removed (each process holds a shared lock on `aot/.<deployment id>.lock` while it uses its table), and only this user's own table folders are touched. **Tests:** `tests/cpu/test_aot_table.py` (new; each trust test fails on the loader before these checks), `tests/cpu/test_aot_table_prune.py` (new; fails on the code before pruning).

### A running server is kept only for the same model and settings

1. **`tpu up` (`remote_setup`):** the chip records the server's command line (model and settings) in `~/.mashbox/serve.args`, and a server that runs keeps running only when its mashbox and that command line are both the same. Otherwise it gets Ctrl-C (SIGINT) and starts again with the new ones, and `up` says so. Before, a server from the same mashbox kept its old settings unless `--restart` was given, so a second Start with the Mac app's Coding agents box ticked left the default context in place.
2. **How callers keep working:** same commands and options; `--restart` still starts a server again with the same settings.

### The engine in a worker process; failures end streams clearly and the server comes back by itself

1. **`runtime/front.py`, `runtime/worker.py`, `runtime/protocol.py` (new):** the HTTP server can run the engine in a worker process it starts and watches (`front.serve_split`, `front.Front`). The front keeps the routes, tokenizer, stop strings, tool-call parsing, waiting queue and limits of `runtime/server.py` (it is `server.Server` with its loop replaced) and sends a request to the worker only when a row is free. Frames are a 4-byte length and a msgpack map, written with the standard library (no new dependency). **How callers keep working:** `mashbox run` still runs the engine in its own process until its command line starts the front; `server.Server` and `server.serve` are unchanged for them.
2. **Failure rules:** a failed device call (a runtime error, out of memory), a call past the watchdog (max(30 s, 10 x its usual time)) or a killed worker restarts the worker. A request whose client has received nothing is sent once more, from the start: a non-streamed request until its response is written (the worker's tokens stay in the front until the request ends, so tokens made before the fault never stop its retry), a streamed request until its first output is sent. A stream that has sent output ends with the route's error event carrying the response id as `request_id` (chat and completions `data: {"error": ...}` then `[DONE]`; Anthropic `event: error`; Responses `event: error` then `response.failed`). A request whose retry fails too gets 500 (`server_error`; Anthropic `api_error`), or the route's error event once its stream has started. While no worker is ready: 503 (Anthropic route 529 `overloaded_error`) with `Retry-After` and `x-should-retry: true`; `/health` adds `worker_pid` and `worker_restarts`.
3. **`runtime/faults.py` (new):** fault injection for failure tests (device error, out of memory, hang, kill, exit at a chosen call, including during the compile warm-up), off unless `MASHBOX_FAULT` or `MASHBOX_FAULTS` names faults.
4. **Stop strings (`runtime/server.py` `complete`):** a non-streamed `/v1/completions` request now reads its tokens as they come, so a stop string ends the row at the engine's next step (it decoded to `max_tokens` before) and nothing past the stop is sent or counted. Streamed `/v1/completions` sends the usage chunk with `stream_options.include_usage`.
5. **Not ready on the Anthropic route is 529** (`overloaded_error`, was 503), with `x-should-retry: true`; the official clients retry on it. One disconnect check (`SSE.closed` calls the request handler's `_gone`).
6. **A model id other than the served one is 404 on the OpenAI routes** (`/v1/chat/completions`, `/v1/completions`, `/v1/responses`; error code `model_not_found`, as OpenAI and vLLM answer); leaving `model` out is accepted. The Anthropic routes answer any model name and echo it, because Claude Code sends its own names for the main model and its subagents. `Front.close()` ends the worker process and the requests still waiting.
7. **Tests:** `test_front_failures.py` (crash mid-stream by device error, out of memory, hang and kill -9 from inside and outside, crash during the compile warm-up, retry once then 500, queued requests untouched), `test_worker_protocol.py`, `test_stop_strings.py` (one process and worker process), `test_api_conformance.py` (openai-python 3.40.0 and anthropic-sdk-python 2.3.0 against the server, including the real engine on a tiny Qwen3.8 model behind a worker process; skips without them); `tests/tpu/front_recovery_check.py` (kill -9 and a device error mid-stream on a chip, cold and restart ready times).
8. **A client that stops reading is ended (`runtime/server.py` `serve`):** once a POST body is read, every write of its answer must finish within 30 s (`handle_one_request` wraps the writer) (`MASHBOX_STALL_S`); a client that reads nothing fills the connection's buffers, the write times out, the request ends as a hang-up (the engine ends the row at its next step, log event `consumer_stalled`, request log finish `consumer_stalled`) and the connection closes. A stream keeps at most 1 MiB in the kernel for its client (`SO_SNDBUF`, capped by `net.core.wmem_max`). Before, the request's thread waited in the write forever and its row ran to `max_tokens`. **How callers keep working:** a client that reads its stream sees no change; the connection's timeout is restored after each answer, so keep-alive connections behave as before. Test: `test_front_failures.py::test_client_that_stops_reading_is_ended_and_its_row_freed` (chat, completions, Anthropic).

### A chip runs the mashbox it was given, mashbox acts only on its own chips, and only guarded servers get a local port

1. **`tpu up` (`remote_setup`, `stage_wheel`):** `MASHBOX_WHEEL` (a file, or an http(s) URL) is copied or downloaded once into the run's private folder and hashed there; that copy is what goes to the chip, the chip checks its sha256 before installing (`MBX_WHEEL_SHA`, nothing installed on a mismatch), and `~/.mashbox/serve.pkg` records `wheel sha256=<hash>` (else `mashbox==<version>`). A wheel that is named but missing, or whose file name is not a wheel name, stops `up` before anything reaches the chip (never an install of something else). The file name is shell-quoted in the chip's command. A running server is reused only when it came from the mashbox this run just installed; otherwise it is started again (Ctrl-C, as `--restart`). Why: a server started from PyPI 0.1.0 (no request guard) kept answering after a guarded wheel was installed, and a URL or a file that changed after the hash could put other bytes on the chip under the recorded hash.
2. **Local port (`Port`, `wait_server`, `hold`):** the chip's server is checked through the SSH forward's private socket, first for readiness, then with another web site's Origin; only a refusal (403, or 401 for a key) opens `127.0.0.1:<port>`. Until then, and after a dropped forward is reopened until it passes again, the port takes connections and closes them unanswered. Each reopen cuts the connections in flight, and a connection checks again after it reached the socket (same forward, still open) before any byte moves, so one that paused across a reopen never reaches the new forward before its check. Anything else (an answer, a 404, no answer) closes the tunnel with the reason and `--restart`. Why: a page in a browser calling 8000-8019 could reach an unguarded server in the window before any check.
3. **Names and zones (`find`, `one_place`, `down`, `ssh`, `tunnel`):** a name the user gives is looked up in every zone (or only in `--zone`), with or without our label. A chip mashbox did not make (no `mashbox` label; every mashbox create sets it) is never waited for, used, set up or deleted, and `up` never creates a second chip with that name in another zone; `down <name>` names it and its zone and exits non-zero instead of "Nothing to take down". A name found in two zones is refused until `--zone` names one, and `down` deletes per zone. A reused chip says when it keeps the max lifetime it was made with. This machine's list (`~/.config/mashbox/tpu.json`) is never proof that a chip is mashbox's, and `status`, `down --all`, `ssh` and `tunnel` without a name list only labelled chips: the list can hold a name from another project or zone, or from a chip deleted since whose name another chip now has. Why: `up --name` had created a second chip with an existing chip's name in an earlier zone, and a stale list entry let `down <name>` delete an unlabelled chip of that name.
4. **Mac app (`ui/app`):** `MASHBOX_APP_WHEEL` (set by the app) becomes `MASHBOX_WHEEL` for every `mashbox tpu` run, also when the file is missing (then `up` stops); run by the Mac app without its wheel, Start answers 409 with the reason. The app checks each tunnel once more on the model's health route (`/health`, `/` for the world model) with a foreign Origin and uses it only on a 403/401. A TPU server row is used (chat, `/v1`, the world page, Connect agent) only while the job that opened its tunnel runs and passed that check at that address; the row is dropped when the job ends and at launch, so a local port another tunnel or program holds later is never addressed as the chip. Server rows added by address stay as they are. `/v1` answers the app makes itself (503, 502) carry `nosniff` and `sandbox`. A signed catalog without a `utc=` signing time is refused. Settings compares the release with the runtime as version numbers and makes no "newer" claim for a build from source (`0.1.0+g<rev>`).
5. **An unclear create answer (`get_chip`, `queue`, `drop_node`, `drop_qr`, `owner`):** after a create that may or may not have gone through (sign-in expired, internal error), the node or queued request of that name is described first and deleted or used only with our label. One without it (another party took the name after the scan) is left as it is and `up` stops naming it and its zone; one that cannot be read is named with the commands to check our label first, never deleted unchecked.
6. **The local port is held until the process exits (`Port.release`, `hold`):** the end of a session cuts the relays and removes the private socket, and the kernel frees the port when the process exits. The Mac app connects to a TPU server first and then requires the same tunnel job to be running and checked (`reach()`: `/v1`, `/api/check`, the world page, files and stream); a job alive on both sides of the connect held the port during it. The app's own guard check counts only if its job still runs after it. Connect your agent shows settings only when the check of the server in use passes.
7. **Two Start or Reconnect clicks at once** make one job: the running-job check and the new job are one step under the jobs lock (the second answers 409). Stop and Delete chip look for the job under the same lock, so a Start being made is stopped too (Delete also stops a run whose command names that chip).
8. **A chip is described again right before each call that reaches it by name (`still_ours`, `owner`):** `up` before its copy (scp), its install, each lifetime probe, each SSH forward (the first, and every retry while the server loads) and each look at the server log; `ssh` and `tunnel` before they connect; `down` before each delete. A chip or queued request of that name without our label (made again since the list or since the last call) is left as it is and the command stops, closing its forward; one gone since counts as gone. A held tunnel whose forward drops describes the chip before it reopens: gone or on its way out (deleting, preempted, terminated) ends the session as before; a chip without our label under that name stops the session with the reason (non-zero, no forward to it); one that cannot be read (network, sign-in) is described again every 10 s and the port relays nothing until it reads as ours. Connect your agent also requires the check to be of the server in use (same address).
9. **A long `TMPDIR`:** the forward's private socket folder moves to `/tmp` when a socket path in `TMPDIR` would pass the system's limit (103 bytes on macOS, 107 on Linux), or `up` stops before ssh saying so; OpenSSH's own lines for a forward it cannot bind (`unix_listener: ...`, `Could not request local forwarding.`) now stop `up` with that message instead of a retry loop until the 45 min limit.
10. **How callers keep working:** same commands and options. New refusals only where mashbox would otherwise act on a chip it did not make, guess between two chips, open a port to an unguarded server, or install bytes it did not hash. **Tests:** `tests/cpu/test_tpu_chip_safety.py` (new), `tests/cpu/test_tpu_cli.py`, `tests/cpu/test_app_tunnel_guard.py`, `tests/cpu/test_app_catalog_sig.py`; each new test fails on the code before its change.

### The app's model catalog is signed

1. **`ui/app/signed.py` (new) + `registry()`:** the default catalog (`CATALOG_URL`, the public repo's models.json, unchanged) is used only when `models.json.minisig` on the app's GitHub release (`CATALOG_SIG_URL`) is a valid MASHBOX Labs signature of the exact bytes (minisign format, Ed25519 checked with the RFC 8032 reference algorithm, stdlib only) and is not older than the signed copy already saved. Otherwise the saved signed copy, else the package's models.json. A catalog address typed in Settings may be unsigned (shown as "not signed"); a signature next to it must match. Tests: `tests/cpu/test_app_catalog_sig.py` (RFC 8032 vector, tampering, rollback, fallbacks).
2. **`POST /api/models/add`:** the seam for adding a Hugging Face model by id; checks the id and answers 501 until GGUF support is in a release (module docstring says where it plugs in).
3. **Settings:** says how updates work when the Mac app runs it (`MASHBOX_APP_UPDATES`, set by the app). No model, server or guard behaviour changes.

### No compile after ready

1. **`runtime/engine.py`:** `Engine.warm` also compiles and runs the helper programs a request runs: the last logits of each prefill row bucket gathered by slot, the sampled first token, logit hashes, slot state take / put / swap and, with the host cache on, its copies, with the arguments a request passes. The first token of new rows is read at each row's slot index, so its programs have one shape whatever the number of rows (a row's draw depends on its seed and token index only, so tokens are unchanged); slot indexes and host copies go to the programs as numpy values, which compiles no per-shape copy program. `prefill(..., lazy=True)` returns (logits, row) pairs. **How callers keep working:** `prefill` without `lazy` returns logits rows as before.
2. **`runtime/programs.py` (new), `cli.py`, `runtime/server.py`:** the warm-up records a signature for every program it compiled (name, static arguments, argument shapes and dtypes) and logs their count and `program_list_sha`; every XLA compile after ready is logged as `{"event": "compile_after_ready", "program": ...}` and `/health` reports `compiles_after_ready`. **`runtime/compile_key.py` (new), `cli.py`:** at start the server computes the compile key and component set (model config and weight layout, kernels, sampler, context and batch shapes, activation-edit capability, program-changing compiler flags, the drafter or none) and logs `{"event": "deployment", ...}`; `/health` reports `deployment_id` and `component_set_sha`, and both are part of the prefix-cache namespace. A compile cache built for another component set is refused (`compile_key.check_cache`). The CPU check E14 (40 mixed requests) and E14_cache (32 conversation turns with prefix and host cache hits, trace on) read 0 compiles after ready. With speculative decoding on (`--mtp`), its programs are not in the warm-up and compile inside the first replies.

### Prefix cache owners: tenant id, namespace, edit variant; full queue is 429

1. **`runtime/tenancy.py` (new), `runtime/server.py` (`key_scope`), `cli.py` (`api_keys`):** the owner of a request is its tenant id, an HMAC of the server's cache secret (32 random bytes per start, rotatable) and the key's tenant or the key itself, never the key's place in the key file. A key-file line may name a tenant after the key (`<key> <tenant>`); keys of one tenant share its prefix cache and its waiting limit. **How callers keep working:** a key file of one key per line reads as before; without keys there is one local owner, as before.
2. **`runtime/engine.py`:** every cached point is keyed by (cache namespace, tenant id, edit variant). `Engine.set_namespace` takes the namespace (`tenancy.namespace`: model and weights, tokenizer, chat template, checkpoint policy) and forgets points of any other; `admit` takes `variant` per request (the hash of its activation-edit table or adapter; None = no edits). Every resume checks the owner key (`IsolationError` if it ever differs). A request that takes a slot holding another tenant's conversation drops that state instead of copying it to host memory on its own path; the host cache evicts with per-tenant floors (cap / tenants present). **How callers keep working:** without scopes, namespace or variant everything is one owner, as before.
3. **Full queue** (`runtime/server.py`, `runtime/openapi.py`): 429 on the OpenAI routes (529 `overloaded_error` on the Anthropic route), with Retry-After; 503 means only that the model is still loading. **How callers keep working:** clients that retry on 429 and 503 retry as before.

### Tensor parallel: the batched engine on 4 chips

1. **`runtime/sampler_tp.py` (new):** sampling when the logits are split on the vocabulary axis over the chips (the lm head leaves them so under `--tensor-parallel-size`). Same settings, order and cuts as `runtime/sampler.py`; a sampled token costs 2 cross-chip exchanges (3 when a top_k / top_p / min_p cut needs the whole row). The noise is made from each token's global id, so for the same logits the draws are the tokens one chip draws.
2. **`models/qwen3_8_27b/shard.py`:** `TPModel.sampler` (the sampler above) and `TPModel.commit` (places the engine's per-slot sampler arrays on the chips, split like the logits); the slot state keeps one placement through every program (constrained going into the forward as well as out), and one zeroing program per state shape is kept, so after the warm-up a request on 4 chips compiles nothing that it would not compile on one.
3. **How callers keep working:** one chip is unchanged: the engine uses a model's `sampler` and `commit` only when the model has them.
4. **`models/qwen3_8_27b/shard.py`, attention reads:** on 4 chips each full-attention layer reads only the cache positions the call attends, never a whole context axis, so a decode step with several rows no longer slows as the context length grows. Tokens and logits are unchanged.

### Speculative decoding (off by default)

1. **`cli.py` (`speculation()`, `download`), `hub.py`, `models.json`, `runtime/drafter.py` (new):** a model row may declare a `drafter` (kind, id, version, the draft file it names, `k_default`, `k_max`, and a `gate` per chip). With no flag, `mashbox run` turns speculation on only where that drafter passed its gate on this chip for this deployment's component set, with `k_default` drafts; anywhere else it stays off with one log line saying why, and the draft file is not fetched. `mashbox run --mtp K` (1 to `k_max`) turns it on with K drafts per verify pass, from the draft file models.json lists (`--mtp-file` for a local copy, its sha256 still checked), and says when it is not gated on this chip; `--mtp 0` turns it off. A model without a draft file, tensor parallel, or a draft file that cannot be fetched stops `--mtp K` with the reason. A draft row may name its own `repo` and `revision`. A drafter may also carry a measured `k_table` per chip (`{rows: k}`, k from 0 to `k_max`): the draft length for each decode row bucket on that chip, where 0 verifies without drafts; buckets it does not name use K. `runtime/drafter.py` holds the declaration view, the gate rule and the drafter's part of the deployment key; the engine refuses a spec module whose `DRAFTER_ABI` differs from its own. While speculation runs, the drafter is part of the deployment's `component_set_sha`; where the gate passed for another component set, `mashbox run` turns speculation off before the warm-up, with one log line (`cli.deployment_keys`). **How callers keep working:** Qwen3.8-27B's drafter declares no passed gate in this release, so without `--mtp` nothing changes and nothing is fetched.
2. **`runtime/engine.py` (`Engine._spec_step`, `spec_programs`), `models/qwen3_8_27b/spec.py` (`make_step`):** speculation runs inside the continuous-batching step. Every decoding row of a step is in one draft / verify / commit program; each row drafts from its own carried input, commits only its own accepted tokens and replays exactly those steps of its linear-attention state, so rejected drafts leave nothing. Requests with `draft: false` and rows within k tokens of max_tokens run with a smaller k, down to 0, in the same program; a k = 0 row commits its plain next token. Sampled and penalised rows speculate too, through the coupled draw: each target token is the draw the sampler without speculation makes at that answer index (same penalties, counted with the drafts before it, same transform, same seeded noise), and drafts are kept while they equal it; there is no rejection sampling. The server serves with speculation on through the same continuous path. `warm()` also runs the speculation programs. **How callers keep working:** with speculation off the engine runs the programs it ran before.
3. **`models/qwen3_8_27b/model.py`, `shard.py`:** `forward` takes `verify` (the target reads a token and its drafts, keeps what the commit replays, commits nothing) and `hidden` (post-norm hidden states for the MTP head). **How callers keep working:** both default to off.
4. **Answers:** with speculation on, an answer (greedy, or sampled with a seed) can differ from the same request without it where two scores tie within one bf16 step (the verify pass and the one-token decode round differently); every committed token is the target's own choice at its position.

### Continuous batching: requests join mid-answer

1. **`runtime/engine.py` (`Engine.admit`, `Engine.step`), `runtime/server.py`:** up to S requests (the slot count) are live at once. A request that arrives while others are mid-answer takes a free slot at the next device call; its prompt is read in chunks next to the decoding rows, and each row ends at its own finish. `generate()` runs on the same path. **How callers keep working:** `generate()` keeps its arguments and result; an engine without `admit`/`step` runs the whole-batch server loop as before.
2. **Waiting limits** (`runtime/server.py`): at most 32 waiting requests per owner (429) and 256 overall (longest-queue drop, else 503; 529 on the Anthropic route), each refusal with `Retry-After` and before any 200. The listen backlog is 1024.
3. **`models/qwen3_8_27b/model.py`, `shard.py`:** `forward` takes `keep` (the rows whose linear-attention state a call may change), so padding rows and rows paused mid-prefill keep their state. **How callers keep working:** `keep` defaults to every row.
4. **Warm-up** (`Engine.warm`): also runs each decode program at 1 step per call, the step the scheduler runs while a row prefills or a request waits.
5. **Speculative decoding** (`--mtp K`, off by default) runs whole batches through `generate()`: a server started with `--mtp K` uses the whole-batch loop.
6. **Answers in a batch:** a greedy answer can differ from the same request run on its own (the row bucket changes the rounding at a near tie).

## 0.1.2

### Version from one source

1. **`models.json`, `src/mashbox/__init__.py`, `pyproject.toml`:** the release version is written once, as the `version` field of `models.json`. `mashbox.__version__` reads the packaged copy, and `pyproject.toml` takes it from `mashbox.__version__` (`dynamic = ["version"]`). The sync check fails when `pyproject.toml` writes a version of its own or `__init__.py` disagrees with `models.json`. **How callers keep working:** `mashbox --version`, `mashbox env` and `mashbox.__version__` give the same string as before.

### Chat speed: no decode compiles mid-reply, server timings, Stop on a half-closed socket

1. **Warm-up** (`Engine.warm_decode`, called by `mashbox run`): runs every decode program a reply can reach (each attention window 128 ... ctx, greedy per row bucket, sampled at S rows) before ready, then clears the slot states. Measured on a TPU v6e-1 (ctx 32768 x 1 slot): a 10-turn chat had 6 decode compiles of ~5 s each inside replies before, 0 after; turn 1 showed 20.0 tok/s before, 38.0 after. Cost: 18 programs, 65.0 s on an empty compile cache, 5.6 s from it. Outputs unchanged (greedy and seeded, before vs after).
2. **`timings`** (llama-server's block: prompt_n, prompt_ms, predicted_n, predicted_ms, predicted_per_second, cache_n, queue_ms) on the last chunk, the usage chunk and plain responses, and in the request log. MASHBOX Chat shows the server's predicted_per_second when it is there.
3. **Stop:** a streamed request also ends when its socket reads EOF (select + 1-byte MSG_PEEK, as llama-server), not only when a write fails; behind an SSH tunnel a write may never fail. CPU test `test_client_half_close_ends_generation`.
4. **Every program before ready, committed slot state** (`Engine.warm`, replaces `warm_decode`): the warm-up also runs every prefill program `prefill()` can choose (`Engine.prefill_shapes`: each chunk bucket x attention window x row bucket), compiling them in 8 threads first, then running each once. The slot state is made on the chip as committed arrays when the weights sit on one device (as `shard.py` does on a mesh): JAX keys a program on whether each argument is committed, and a fresh state was not, so the first prefill and decode after each new state were programs of their own that no warm-up ran (the 5.4 s sampled compile left open above). Measured on a TPU v6e-1 with an empty compile cache: ctx 2048 x 8 runs 102 prefill + 20 decode programs, ready in 339.9 s the first time and 47.2 s from the cache; ctx 32768 x 1 runs 50 + 18, ready in 122.1 s. After ready, the only compiles in a 3-turn chat at 2048 x 8 and a 10-turn chat plus 5 more requests at 32768 x 1 were `put` and `stack` (0.14-0.2 s). First reply at 2048 x 8, Recommended preset: 32.7 tok/s, first token 0.36 s (was 17.4 tok/s and 7.42 s on main). Outputs unchanged (greedy chat 3/3 turns, seeded and greedy requests). CPU test `tests/cpu/test_engine_warm.py` (no program added after the warm-up across prompt lengths, rows, greedy and sampled, cached and restored turns).
5. **Sampled rows and the shipped compile cache:** sampled rows run all S rows (32.7-33.0 tok/s for one user at 8 slots, 38.1 at 1 slot). The compile cache shipped for TPU v6e with JAX 0.11.2 holds every program the warm-up compiles: with the weights on disk, a start on TPU v6e-1 is ready in 69.6 s at 2048 x 8 and 32.6 s at 32768 x 1, against 326.6 s on an empty compile cache.

### Inference server and chat template security fixes

1. **`runtime/chat.py`:** control tokens come only from the template. A literal `<|im_end|>`, `<|im_start|>` or `</tool_response>` in a message, tool result, tool call or tool definition is tokenized as plain text, so text an agent reads cannot forge a user or system turn. A chat whose strings hold no control-token text gets the same ids as before (one pass; checked with the shipped Qwen tokenizer).
2. **`runtime/server.py`:** every request passes `runtime/guard.py`: Host must be localhost, 127.0.0.1, [::1], an IP address or the server's own `--host` (a DNS-rebinding page is refused, 403); a present Origin must be the server's own (403); a POST must be `application/json` (415), so a web page cannot send one without a CORS preflight, which the server never approves. Clients that are not browsers (curl, SDKs, coding agents) pass as before. `/health` stays open.
3. **API keys, `cli.py` and `runtime/server.py`:** `--api-key-file FILE` (one key per line) or `MASHBOX_API_KEY=k1,k2` makes every `/v1` request need a key (`Authorization: Bearer` or `x-api-key`, 401 otherwise). On a `--host` that is not loopback a key is made once in `~/.config/mashbox/api-key` (mode 0600) and only its path is printed. On 127.0.0.1 nothing changes for the documented agent setups. A key source that holds no key (an empty key file, `MASHBOX_API_KEY` with only commas) stops the start instead of serving with no key.
4. **`runtime/engine.py`:** every prefix-cache point belongs to the scope (API key) of the request that made it, and a prompt resumes only from its own scope's points, so one key's prompts are never served from, or reported as cached by, another key's. Without keys there is one scope, as before.
5. **Tests:** `tests/cpu/test_serve_security.py` (each refused request against the real handler).
6. **`tpu/__init__.py` (tunnel):** `mashbox tpu up` / `tunnel` bind the local port themselves and keep it for the whole session (tunnel drops included), relaying each connection to the SSH forward, which listens on a Unix socket in a private (0700) directory with its log; so another user of the same machine can neither take the port nor answer in the chip's place. "Server ready" needs our SSH process running; a forward SSH cannot set up stops with its message and the take-down command. Chip names, zones and projects are checked before any gcloud call. ### `mashbox tpu up` deletes a create that may have gone through

1. **`src/mashbox/tpu/__init__.py`:** a plain create that ends in an error that is not a clear refusal (an expired sign-in, or an error `up` does not know), or that was made and then never reached READY, is deleted by its exact name in that zone before `up` tries the next zone or stops. When that delete fails too (the sign-in is still expired), `up` stops with the chip's name, zone and both delete commands (`mashbox tpu down <name>` and the `gcloud compute tpus tpu-vm delete` line). A queued request that ends in such an error counts as made: it is watched like the others (it can be the one granted) and deleted by name when `up` ends. A plain node or queued request that already existed under that name ("already exists") was not made by this command: `up` never uses or deletes it. A queued request that is already gone counts as deleted ("not there"); a failed delete prints its `gcloud` line. Why: when the sign-in expired during a create, `up` stopped with "gcloud is not signed in" while Google went on creating the chip, without telling the person, and an unknown error on a queued request was read as a refusal. Compatible: same commands and options; clear refusals (no capacity, quota, no access, API off, billing) behave as before.
2. **Also in `mashbox tpu` (from review):** a node that already existed under that name (create says "already exists") stops `up` with its zone and is never waited for, set up, saved or deleted, READY or not; one failed describe while a new chip starts is not read as "gone" (3 in a row are); any stop after the chip exists (install, server start) ends with the chip's name and `mashbox tpu down <name>`, and a failed list there no longer says "Nothing was changed"; `down` goes on to its other chips when the check list after a delete fails; `down --zone` and `status --zone` look in that zone only, a way past a zone whose list always fails (the error says so); Google's error messages with quotes in them are shown whole.
3. **`life.sh`:** the time left is read after the script fetch, so a reboot seconds before the deadline cannot arm a calendar time already past (which never fires); 2 s or less left deletes at once.
4. **Tests:** `tests/cpu/fake_gcloud.py` gains `accepted-auth` and `accepted-internal` for plain creates and queued requests (made, then the call fails; `accepted-auth` leaves the sign-in expired). `tests/cpu/test_tpu_cli.py` covers each of these cases.

At their pins, Hy-Nomas (Tencent) and Qwen3.8-27B (Qwen) are both Apache-2.0. This supersedes "not chosen yet" in the docs entry further down, which stays as history.
2. **`pyproject.toml`:** `license = "Apache-2.0"` and `license-files = ["LICENSE", "LICENSE-KERNELS"]` (PEP 639); the build backend needs `setuptools>=77`. Why: PyPI shows no licence for 0.1.0. Compatible: the wheel holds the same files; its METADATA gains `License-Expression: Apache-2.0`.
3. **`models.json` and its packaged copy:** `upstream.license_sha256` per model (the pinned upstream LICENSE file). Hy-Nomas `upstream.components` lists the Tencent code commit (`hymm/`, `configs/`) and the Qwen2.5-VL-7B-Instruct text encoder (apache-2.0 on its card; that repo has no LICENSE file). Compatible: new fields; only the sync check reads them.
4. **Cards (`templates/hf/card-*.md`, `hf/*/README.md`):** the licence line reads "Weights: <licence> licence, from <upstream>@<revision>; code: Apache-2.0 (MASHBOX Labs)" and links the upstream LICENSE in the model's Hugging Face repo. With the next card upload, `licenses/<id>/LICENSE` goes to that repo as `LICENSE`, unchanged.
5. **`docs/models/hy-nomas.md`:** "Our code in this repo: licence not chosen yet" now says Apache-2.0, as `LICENSE` has since 0.1.0. `docs/licence.md` names each model's weights licence and the revision it was read at.
6. **`tools/hf_github_sync_check.py`:** `check` (T0) and `licence` fail on a licence mismatch with `models.json`: `LICENSE` is not the Apache-2.0 text, the pyproject licence differs, `licenses/<id>/LICENSE` is not the pinned file, a component revision differs from the model's `upstream.json`, or a page, card or card template says a licence is not chosen, pending or reserved (this file's history excepted). `--online` also fails when a public model repo has no `LICENSE` equal to the pinned upstream file. It never edits. Test: `test_licence_check_catches_drift`.

### Install on a TPU VM (Python 3.12 through uv)

On the TPU VM image `v2-alpha-tpuv6e` (Ubuntu 22.04, Python 3.10.12, pip 22.0.2):

1. **Install line (README, `docs/google-cloud.md` step 7, `AGENTS.md`, `templates/hf/card-llm-tpu.md`, `docs/_templates/model.md`):** `python3 -m pip install "mashbox[tpu]"` failed on the chip with `No matching distribution found for jax[tpu]==0.11.2`, because jax and jaxlib 0.11.2 need Python 3.12. The line is now `python3 -m pip install uv && python3 -m uv tool install --python 3.12 "mashbox[tpu]"`: uv brings its own Python 3.12 and puts the `mashbox` command in `~/.local/bin`, so commands use `~/.local/bin/mashbox` in place of `python3 -m mashbox`. Measured on the chip: 6.9 s, 5.6 s and 4.8 s for the whole install (three new users). Compatible: the package and CLI are unchanged; `python3 -m mashbox` still works from any Python 3.12 environment that has it. Other card templates (`card-world.md` and the rest) and `docs/models/hy-nomas.md` kept the old line in this version; the TPU VM images have Python 3.10, so the same change applies to them.
2. **`pyproject.toml`:** `requires-python` is `>=3.12` (was `>=3.10`). Why: the `tpu`, `cpu` and `dev` extras pin jax 0.11.2, which needs 3.12; with `>=3.10`, pip on 3.10 installs the package and then fails on JAX with a less clear message. Compatible: no supported setup ran on 3.10 or 3.11.
3. **`.github/workflows/ci.yml`:** CPU tests run on Python 3.12 (was 3.10), for the same reason: `pip install -e ".[dev]"` cannot install jax 0.11.2 on 3.10.
4. **`hub.py`:** downloads from Hugging Face use plain HTTPS unless the user sets `HF_HUB_DISABLE_XET` (the module sets it to `1` with `setdefault`, before `huggingface_hub` is imported). Why: Xet downloads of the 26.9 GB weights file on new TPU VMs could stop with `HTTP 429 Too Many Requests` from the Xet CDN (ending `mashbox run` with a traceback) or stall, while HTTPS finished at 200 to 230 MB/s in europe-west4-a. Compatible: same files, same sha256 checks; `HF_HUB_DISABLE_XET=0` gives the old behaviour.
5. **`CONTRIBUTING.md`, `.github/ISSUE_TEMPLATE/bug.yml`:** the env command is `~/.local/bin/mashbox env`.
6. **`runtime/server.py`:** the batching loop waits up to `GATHER_S` (20 ms) after the first queued request for others before it starts a batch (requests with `"merge": false` do not wait). Why: requests sent together reach the queue a few milliseconds apart, so the first one ran alone and the rest waited for its whole answer. Measured on TPU v6e-1 with Qwen3.8-27B (8 users, 128 new tokens each, greedy): 8 users in a closed loop for 60 s went from 76.9 to 258.0 tokens/s in total (median request 7.74 s to 3.97 s); 8 streamed requests sent together went from a first token at 3.51 s for 7 of them to 0.11 s for all 8. Cost: one user alone gets the first token 20 ms later (32 ms to 52 ms) and 37.45 instead of 37.75 tokens/s (one run each). Compatible: same routes, outputs and options; the module docstring now says that requests arriving while a batch runs wait for it to finish.

### Qwen3.8-27B weights file

1. **`hub.weights_file`:** picks from the `files[]` rows whose `kind` is `weights` (a row without `kind` counts as weights), the one marked `"default": true` when no name is given, else the first. Why: `files[]` can now hold other kinds (a compile-cache file), which must never be loaded as weights. Compatible: a list of plain weight rows behaves as before.
2. **`hub.compile_cache` (new) and `cli.load`:** before loading, `cli.load` asks `hub.compile_cache` for a `files[]` row with `kind` `xla-cache` whose `chips`, `jax`, `jaxlib` and `libtpu` match the running setup. If one exists, it downloads the tar at the pinned revision, checks its sha256 and unpacks its flat entries into the compile-cache directory (entries already there are kept). Why: a first run then loads its compiled programs instead of compiling them (on TPU v6e-1 with Qwen3.8-27B: 44.0 s to ready without a cache, 25.5 s with one, both including the first sha256 check of the weights). Compatible: with no such row (every model today) it logs one line and does nothing; any error is logged and the run continues.
3. **`kernels.decode_kernels`:** if a payload in the kernel bundle cannot be read, the model runs on plain JAX and logs one line, as it already does for a chip or JAX mismatch. Why: on a new TPU VM, `jax.export` failed with `ImportError: Please install 'flatbuffers'` and the run stopped. Compatible: a readable bundle loads as before.
4. **`pyproject.toml`:** `flatbuffers` added to the dependencies. Why: JAX needs it to read the kernel bundle and does not install it itself. Compatible: one added pure-Python dependency.
5. **`models.json`, `qwen3-8-27b` row only:** `files[]` lists `Qwen3.8-27B-BQ8_R.bshj` (sha256, size, bits per weight, measured quality and speed), `base_model_relation` is `quantized`, `results[]` has the measured speed and start-to-ready rows, and `hf_revision` pins the Hugging Face commit that holds the file.

### Coding agents: Anthropic Messages, OpenAI Responses, tool calls, prefix cache

Claude Code, Codex and Pi now run against `mashbox run qwen3-8-27b` (guide: `docs/agents-on-tpu.md`).

1. **`runtime/agents.py` (new) and `runtime/server.py`:** `POST /v1/messages` and `/v1/messages/count_tokens` (Anthropic Messages, for Claude Code), `POST /v1/responses` (OpenAI Responses, for Codex), and tools in `/v1/chat/completions`. Tool calls are rendered and parsed in the model's own chat-template format, also while streaming. Images, files and tools that run on the provider's servers are refused with an error that names them (Codex's hosted `web_search` is left out of the tool list and logged as `dropped_tools`). Every request logs one JSON line (`event: request`: api, client, prompt and cached tokens, time to first token). `MASHBOX_DUMP_DIR` keeps request bodies for debugging. How existing callers keep working: `/v1/completions` is unchanged; in `/v1/chat/completions` a missing `max_tokens` now means up to the end of the context (was 512), a `max_tokens` larger than what is left is lowered instead of refused, and thinking output (with `enable_thinking`) comes back as `reasoning_content` instead of inside `content`.
2. **`runtime/engine.py`:** prefix cache, off unless `Engine(prefix_cache=True)`. With it, slot state lives on between calls and each slot keeps host copies of its linear-attention state at the start of the last message and at the end of the prompt; a prompt that starts with a cached one prefills only the new tokens. Without it `generate` runs as before (tiny-model checks T1 to T7 pass on the changed engine). With `S <= 2` the model's scratch slot is not allocated (no call has padding rows then).
3. **`cli.py`:** the server turns the prefix cache on (`--no-prefix-cache` turns it off); above `--ctx 8192` prefill chunks shrink so long contexts fit in chip memory.
4. **Tests:** `tests/cpu/test_agent_api.py` (three APIs, streamed and not, against a scripted engine with the real tokenizer and template; set `MASHBOX_QWEN_UPSTREAM`), `tests/cpu/prefix_cache_checks.py WD` (tiny model: restored state gives the same logits, cached turns decode the reference argmax, two conversations keep their own slots).

### One repo for every model

The repo was put together from two model releases: Qwen3.8-27B, which brought the package core (CLI, downloads, BSHJ reader, kernel loader, LLM runtime), and Hy-Nomas, which brought its model folder, browser app, docs page and licence. Changes to the core made while merging:

1. **`cli.py`:** `RUNNABLE` lists the models whose runtime is in this version (`qwen3-8-27b`). `mashbox run` and `mashbox download` for any other model in `models.json` print one line pointing to that model's docs page and exit with code 2. Why: `hy-nomas` has a row in `models.json`, but its runtime port is not in this version; without the check, `run hy-nomas` would start downloading files that only the LLM runtime uses.
