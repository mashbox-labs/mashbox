# Core changes

Every change to the shared core (listed in [OWNERS.md](OWNERS.md)) gets an entry here: what changed, why, and how existing models keep working. Newest first.

## Unreleased, 2026-10-28: package description

1. **`pyproject.toml`, `src/mashbox/__init__.py`, `src/mashbox/cli.py`:** the package description and module docstring, and a new `mashbox --help` description, read "mashbox by MASHBOX Labs: open models that run faster and cheaper." Text only: no behaviour, API or model change, so every model keeps working as before.

## Unreleased, 2026-10-28: CI tiers

1. **`.github/workflows/ci.yml`:** one T0 job on every change (pytest `-m t0 tests/cpu/test_core.py` and `ruff --select E9,F63,F7,F82`, no package install), then T1 only for the areas the change touches, one job per area, with CPU torch from the PyTorch CPU index (the CUDA wheels were about 2.7 GB that no test used). The separate offline sync check step is gone: `test_views_match_models_json` already runs it. Why: every change, docs included, took 6 min 27 s. Compatible: the same tests run; a docs-only change now runs T0 alone.
2. **`tests/conftest.py`, `tools/ci_select.py` (new):** markers from file names (`<model id with underscores>` or `core`, `t0` for `test_core.py`), plus `slow`, `cpu_only` and `quarantine(reason, until)`; `ci_select.py` maps changed paths to areas from `models.json`, so a new model needs no CI edit. No test file moved.
3. **`tests/cpu/test_core.py`:** `test_models_json_copy` stays byte-exact but now names the first differing JSON field and the fix (`cp models.json src/mashbox/models.json`); new `test_every_test_module_says_what_it_guards` (module docstrings; `test_hy_nomas.py` is the one known exception until its owner adds one).
4. **`tools/ci_tpu_gate.py`, `tools/ci_tpu_job.sh`, `tests/tpu/hy_nomas_kernel_tolerances.json` (new):** the chip tier T2 (CI.md): version pins, kernel gates with written tolerances, the CPU suite on the chip.
5. **`sync.yml`, `tpu-status.yml`:** Python 3.12; `tpu-status.yml` exits cleanly while the `status` branch does not exist yet.

## Unreleased, 2026-10-28: first-time user run on TPU v6e-1 (Qwen3.8-27B)

Found by following the README on a new on-demand TPU v6e-1 as a first-time user (image `v2-alpha-tpuv6e`: Ubuntu 22.04, Python 3.10.12, pip 22.0.2).

1. **Install line (README, `docs/google-cloud.md` step 7, `AGENTS.md`, `templates/hf/card-llm-tpu.md`, `docs/_templates/model.md`):** `python3 -m pip install "mashbox[tpu]"` failed on the chip with `No matching distribution found for jax[tpu]==0.11.2`, because jax and jaxlib 0.11.2 need Python 3.12. The line is now `python3 -m pip install uv && python3 -m uv tool install --python 3.12 "mashbox[tpu]"`: uv brings its own Python 3.12 and puts the `mashbox` command in `~/.local/bin`, so commands use `~/.local/bin/mashbox` in place of `python3 -m mashbox`. Measured on the chip: 6.9 s, 5.6 s and 4.8 s for the whole install (three new users). Compatible: the package and CLI are unchanged; `python3 -m mashbox` still works from any Python 3.12 environment that has it. Other card templates (`card-world.md` and the rest) and `docs/models/hy-nomas.md` still carry the old line: their owners should switch them, since every TPU image we use has Python 3.10.
2. **`pyproject.toml`:** `requires-python` is `>=3.12` (was `>=3.10`). Why: the `tpu`, `cpu` and `dev` extras pin jax 0.11.2, which needs 3.12; with `>=3.10`, pip on 3.10 installs the package and then fails on JAX with a less clear message. Compatible: no supported setup ran on 3.10 or 3.11.
3. **`.github/workflows/ci.yml`:** CPU tests run on Python 3.12 (was 3.10), for the same reason: `pip install -e ".[dev]"` cannot install jax 0.11.2 on 3.10.
4. **`hub.py`:** downloads from Hugging Face use plain HTTPS unless the user sets `HF_HUB_DISABLE_XET` (the module sets it to `1` with `setdefault`, before `huggingface_hub` is imported). Why: on 28 October 2026, 3 of 4 Xet downloads of the 26.9 GB weights file on new TPU VMs failed (twice `HTTP 429 Too Many Requests` from the Xet CDN, which ended `mashbox run` with a traceback after 84 s and 135 s; once a stall at 10.8 GB), while HTTPS finished in every try (200 to 230 MB/s in europe-west4-a over two runs, about 94 MB/s in us-east5-b). Compatible: same files, same sha256 checks; `HF_HUB_DISABLE_XET=0` gives the old behaviour.
5. **`CONTRIBUTING.md`, `.github/ISSUE_TEMPLATE/bug.yml`:** the env command is `~/.local/bin/mashbox env`.
6. **`runtime/server.py`:** the batching loop waits up to `GATHER_S` (20 ms) after the first queued request for others before it starts a batch (requests with `"merge": false` do not wait). Why: requests sent together reach the queue a few milliseconds apart, so the first one ran alone and the rest waited for its whole answer. Measured on TPU v6e-1 with Qwen3.8-27B (8 users, 128 new tokens each, greedy): 8 users in a closed loop for 60 s went from 76.9 to 258.0 tokens/s in total (median request 7.74 s to 3.97 s); 8 streamed requests sent together went from a first token at 3.51 s for 7 of them to 0.11 s for all 8. Cost: one user alone gets the first token 20 ms later (32 ms to 52 ms) and 37.45 instead of 37.75 tokens/s (one run each). Compatible: same routes, outputs and options; the module docstring now says that requests arriving while a batch runs wait for it to finish.

## Unreleased, 2026-10-28: Hy-Nomas runtime

1. **`cli.py`:** `RUNNABLE` now lists `hy-nomas`, and a new `MODEL_CLI` map (`{"hy-nomas": "mashbox.models.hy_nomas"}`) hands `run <id>` and `download <id>` for those models to the model package's `main(cmd, argv)`, before the shared parser runs. Why: Hy-Nomas needs its own options (`--ui`, `--out`, `--world`, `--keys`, `--preset`, `--port`, `--stub`), which Qwen's parser does not have. Compatible: models not in `MODEL_CLI` (Qwen) go through the same parser, options and `cli.load` as before; `env` is unchanged.
2. **`pyproject.toml`:** a new extra `hy-nomas` (`torch>=2.5`, `transformers==4.57.1`, `pyyaml`, `scipy`, `imageio-ffmpeg`, `pillow`): Tencent's own prompt, tokenizer and camera code runs on the host CPU and needs these. Package data also takes `models/*/*.html`, so the installed package can serve `hy_nomas/page.html` (a copy of `apps/hy-nomas/page.html`; a test checks they match). Compatible: `mashbox[tpu]` installs exactly what it did before; the extra is opt-in.
3. **`tests/cpu/test_core.py`, `test_imports_are_public`:** a file inside `src/mashbox/models/<pkg>/` may also import the packages of the pyproject extra named after its model id, and the top-level folders its `upstream.json` pins by commit and tree hash (`code.keep`, here Tencent's `hymm` and `configs`). Why: the Hy-Nomas runtime imports torch and Tencent's code, which were declared but not allowed by the check. Compatible: core files and models without an extra or an `upstream.json` are checked against the same list as before.
4. **`OWNERS.md`:** the `hy-nomas` row lists its two new test files. No rule changed.

## Unreleased, 2026-10-28: Qwen3.8-27B weights file

1. **`hub.weights_file`:** picks from the `files[]` rows whose `kind` is `weights` (a row without `kind` counts as weights), the one marked `"default": true` when no name is given, else the first. Why: `files[]` can now hold other kinds (a compile-cache file), which must never be loaded as weights. Compatible: a list of plain weight rows behaves as before.
2. **`hub.compile_cache` (new) and `cli.load`:** before loading, `cli.load` asks `hub.compile_cache` for a `files[]` row with `kind` `xla-cache` whose `chips`, `jax`, `jaxlib` and `libtpu` match the running setup. If one exists, it downloads the tar at the pinned revision, checks its sha256 and unpacks its flat entries into the compile-cache directory (entries already there are kept). Why: a first run then loads its compiled programs instead of compiling them (on TPU v6e-1, 2026-10-28, Qwen3.8-27B: 44.0 s to ready without a cache, 25.5 s with one, both including the first sha256 check of the weights). Compatible: with no such row (every model today) it logs one line and does nothing; any error is logged and the run continues.
3. **`kernels.decode_kernels`:** if a payload in the kernel bundle cannot be read, the model runs on plain JAX and logs one line, as it already does for a chip or JAX mismatch. Why: on a new TPU VM, `jax.export` failed with `ImportError: Please install 'flatbuffers'` and the run stopped. Compatible: a readable bundle loads as before.
4. **`pyproject.toml`:** `flatbuffers` added to the dependencies. Why: JAX needs it to read the kernel bundle and does not install it itself. Compatible: one added pure-Python dependency.
5. **`models.json`, `qwen3-8-27b` row only:** `files[]` lists `Qwen3.8-27B-BQ8_R.bshj` (sha256, size, bits per weight, measured quality and speed), `base_model_relation` is `quantized`, `results[]` has the measured speed and start-to-ready rows, and `hf_revision` pins the Hugging Face commit that holds the file.

## Coding agents, 2026-10-28: Anthropic Messages, OpenAI Responses, tool calls, prefix cache

Claude Code, Codex and Pi now run against `mashbox run qwen3-8-27b` (guide: `docs/agents-on-tpu.md`).

1. **`runtime/agents.py` (new) and `runtime/server.py`:** `POST /v1/messages` and `/v1/messages/count_tokens` (Anthropic Messages, for Claude Code), `POST /v1/responses` (OpenAI Responses, for Codex), and tools in `/v1/chat/completions`. Tool calls are rendered and parsed in the model's own chat-template format, also while streaming. Images, files and tools that run on the provider's servers are refused with an error that names them (Codex's hosted `web_search` is left out of the tool list and logged as `dropped_tools`). Every request logs one JSON line (`event: request`: api, client, prompt and cached tokens, time to first token). `MASHBOX_DUMP_DIR` keeps request bodies for debugging. How existing callers keep working: `/v1/completions` is unchanged; in `/v1/chat/completions` a missing `max_tokens` now means up to the end of the context (was 512), a `max_tokens` larger than what is left is lowered instead of refused, and thinking output (with `enable_thinking`) comes back as `reasoning_content` instead of inside `content`.
2. **`runtime/engine.py`:** prefix cache, off unless `Engine(prefix_cache=True)`. With it, slot state lives on between calls and each slot keeps host copies of its linear-attention state at the start of the last message and at the end of the prompt; a prompt that starts with a cached one prefills only the new tokens. Without it `generate` runs as before (tiny-model checks T1 to T7 pass on the changed engine). With `S <= 2` the model's scratch slot is not allocated (no call has padding rows then).
3. **`cli.py`:** the server turns the prefix cache on (`--no-prefix-cache` turns it off); above `--ctx 8192` prefill chunks shrink so long contexts fit in chip memory.
4. **Tests:** `tests/cpu/test_agent_api.py` (three APIs, streamed and not, against a scripted engine with the real tokenizer and template; set `MASHBOX_QWEN_UPSTREAM`), `tests/cpu/prefix_cache_checks.py WD` (tiny model: restored state gives the same logits, cached turns decode the reference argmax, two conversations keep their own slots).

## 0.1.0, 2026-10-28: one repo for every model

The repo was put together from two model releases: Qwen3.8-27B, which brought the package core (CLI, downloads, BSHJ reader, kernel loader, LLM runtime), and Hy-Nomas, which brought its model folder, browser app, docs page and licence. Changes to the core made while merging:

1. **`cli.py`:** `RUNNABLE` lists the models whose runtime is in this version (`qwen3-8-27b`). `mashbox run` and `mashbox download` for any other model in `models.json` print one line pointing to that model's docs page and exit with code 2. Why: `hy-nomas` has a row in `models.json`, but its runtime port is not in this version; without the check, `run hy-nomas` would start downloading files that only the LLM runtime uses. Compatible: Qwen's commands, options and `cli.load` are unchanged.
2. **`pyproject.toml`:** package data also takes `models/*/*.json`, because `hy-nomas` keeps `defaults.json` and `worlds.json` in its model folder. Compatible: it only adds files to the package.
3. **`models.json`:** one registry with both rows, `github.repo` = `mashbox`. The `hy-nomas` row now pins `hf_revision` `e3e5a785eecdc9cb29a0a79c9592f3ef2c9a7c13`, the Hugging Face revision that holds its kernel bundle (sha256 checked against the row). The `qwen3-8-27b` row is unchanged.
4. **`tools/hf_github_sync_check.py`:** without `--templates`, it reads card templates from `<repo>/templates/hf` when that folder exists, and from its old default otherwise. The templates now live in `templates/hf/` in this repo, so CI's `check --repo . --offline` finds them. Compatible: an explicit `--templates`, and trees without `templates/hf`, behave as before.
5. **`tools/tpu_status.py`:** added. `.github/workflows/tpu-status.yml` already called it.
6. **Tests:** `tests/cpu/test_package.py` is split into `tests/cpu/test_core.py` (registry copy, folders per model, public imports, views in sync, the `RUNNABLE` check) and `tests/cpu/test_qwen3_8_27b.py`. Renamed so each model's tests carry its id: `tests/cpu/run_cpu_checks.py` is now `tests/cpu/qwen3_8_27b_checks.py`, and `tests/tpu/smoke_tpu.py` is now `tests/tpu/qwen3_8_27b_smoke.py`. Only their usage lines changed. Scripts that call the old paths must use the new ones.
7. **Docs:** `README.md`, `AGENTS.md`, `llms.txt`, `docs/SUMMARY.md` and `docs/google-cloud.md` cover both models. Step 6 of `docs/google-cloud.md` now runs `qwen3-8-27b`, which fits the v6e-1 chip that step 5 creates (`hy-nomas` needs a v6e-4). The install line is `pip install "mashbox[tpu]"` everywhere. The serving steps and options from the Qwen-only README moved to `docs/models/qwen3-8-27b.md`. `CONTRIBUTING.md` and the pull request template add the step that copies `models.json` to `src/mashbox/models.json`. The README no longer calls the code "open source" while `LICENSE` reserves all rights.
